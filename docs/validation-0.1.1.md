# 0.1.1 修复与验收记录

日期：2026-08-27。状态：后台回归通过；选择、工作区重新选择和取消已获用户确认，本次 picker bug 验收通过。范围为 0.1.1 解包版，安装包/便携包入口仍待单独验收。

后续源码本地提交、依赖锁定及干净构建结果见[构建复现记录](reproducible-build.md)；下文保留 picker 修复阶段的检查顺序。

## 问题与修复

0.1.0 可以弹出文件夹对话框，但选择目录后 worker 在 `readUtf16` 的 `koffi.view` 调用处崩溃，退出码 134，错误为 `FATAL ERROR: Error::New napi_get_last_error_info`。这与缺少 conpty 二进制不是同一个问题。

原生字符串改用 `koffi.decode(address, 'char16', -1)` 复制，避免 Electron 不支持的外部 ArrayBuffer 和 UTF-16 低字节误判。COM 字符串在 `finally` 释放。IPC 仅在 `done` 或 `error` 发送完成后关闭；异常退出带上退出码和信号。构建脚本将原生目录选择包加入覆盖清单，并检查 conpty 二进制。

## 再次报错后的对照复测

2026-08-27，用户再次反馈同一错误后，后台检查发现主进程 PID 67996 仍来自 `dist/win-unpacked/DSH Desktop.exe`，其 DSH 子进程也加载该目录下的运行时。读取对应 `app.asar/package.json` 确认版本为 0.1.0；`dist/0.1.1/win-unpacked/` 中的包内版本为 0.1.1。

对这两份打包运行时分别执行同一套 `test:picker`：旧版普通路径和 Unicode 路径均在 `readUtf16` 崩溃，退出码 134，取消通过（1/3）；新版三项通过（3/3）。测试隔离了模态 COM 调用，没有打开窗口或终止用户进程。根目录 npm 输出的 0.1.1 是测试工具所属项目版本，不代表被测旧产物的版本。

该次检查只能确认当时运行的是旧产物，不能认定新版实际 UI 已通过。下一步要求用户完全退出旧程序、启动明确的 0.1.1 路径，再核对进程位置并进行真实选择、回填与取消验收。单实例机制会让第二次启动聚焦已有窗口，但未观察到用户的启动过程，不能断言这就是此次仍在旧版的具体原因。

## 剩余检查与 bug 关闭

用户随后明确反馈“重新选择是没问题的”。澄清“取消”指点击「添加工作区…」后在系统文件夹窗口取消本次操作（返回 DSH、保持原工作区、不新增工作区、不报错），不是清空当前工作区后，用户回复“没问题”。

据此记录选择、工作区重新选择和取消三项用户实测通过，关闭本次 worker 崩溃 bug。验收依据是前述 0.1.1 进程核对、用户截图及明确反馈，并非代理代为操作。无需添加“取消当前工作区”按钮。

安装包和便携包入口仍未单独进行用户验收，不能把本次结论扩展为整个客户端的完整发布验收。本轮仅更新文档与发布状态记录，未修改代码或重新打包。

## 桌面框架取舍

保留 Electron，先修复局部原生模块兼容性。Electron 官方说明外部 ArrayBuffer 受内存隔离限制，可通过复制数据适配；必要时也能随应用附带独立 Node.js 后台。Tauri 仍需要以 sidecar 打包和管理 DSH 后台，不会省去此项工作。

依据：[Electron 内存隔离说明](https://www.electronjs.org/blog/v8-memory-cage)、[Tauri 外部程序打包](https://v2.tauri.app/develop/sidecar/)。
